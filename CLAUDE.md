# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Product

WORKHUB is a multi-tenant Agile/Scrum project management platform. The full business spec (Vietnamese) is [docs/requirements.md](docs/requirements.md); read the relevant section before building a module. It also defines the milestone order (M0–M11).

Domain hierarchy: User → Workspace → Team → Project → (Backlog/Issues, Sprints, Board, Documents, Meetings, Reports, Chat/Notifications). A user can belong to many Workspaces, Teams and Projects.

Decisions and rules that shape the code:
- **Modular monolith.** One Spring Boot app; each domain module (auth, workspace, team, project, issue, sprint, ...) gets its own package under the base package.
- **Scoped RBAC.** Roles are assigned per Workspace, Team or Project membership, never as one global role per user. Scrum responsibilities (Product Owner, Scrum Master, Developer) are project-scoped. Every permission check must be enforced in the backend; hiding UI is not enough.
- **History is data.** Burndown/Burnup/Velocity must be rebuilt from recorded history (scope added/removed, status transitions, daily snapshots), so sprint scope changes and issue status changes must be persisted as events/snapshots, not just overwritten. Sprint Backlog keeps its scope at sprint start.
- **Product Backlog ≠ Sprint Backlog.** Backlog is project-scoped in the MVP; one Scrum Team per Project in the MVP.
- Sprint status: Future → Active → Completed (or Cancelled), max one month. Ending a sprint never auto-marks issues Done; unfinished issues go back to the backlog or the next sprint.
- Story Points are relative size, separate from time estimates (Original/Remaining Estimate).
- Realtime is WebSocket; collaborative document editing must use a CRDT (Yjs), not whole-document overwrite.

## Layout

Monorepo with two independent projects and no root build tool:

- `backend/` — Spring Boot 4.1 (Java 21, Maven wrapper). Base package `com.workhub`, one package per domain module, not per layer: `auth/` (register, login, tokens, email flows), `user/` (profile, `/api/me`), `workspace/`, `team/`, `project/`, `issue/`, `sprint/`, `board/`, `report/`, `document/`, `meeting/`, `notification/`, `alert/`, `chat/`, `realtime/`, `audit/`, `export/`, `invitation/`, `access/` (RBAC), `security/` (JWT + Spring Security), `common/` (error handling, `Clock`, `SecureTokens`, helpers).
- `frontend/` — React 19 + Vite + TypeScript SPA with React Router 7. UI text is Vietnamese.
- `docker-compose.yml` — PostgreSQL 17 for local development, published on host port **5433** (override with `POSTGRES_PORT`), because 5432 is taken by another project's database on this machine.

Run backend commands from `backend/` and frontend commands from `frontend/`.

## Commands

Backend (`backend/`):

```sh
./mvnw spring-boot:run                                   # API on http://localhost:8080 (H2 in-memory)
SPRING_PROFILES_ACTIVE=postgres ./mvnw spring-boot:run   # use PostgreSQL (start it first: docker compose up -d, from repo root)
./mvnw test                                              # all tests
./mvnw test -Dtest=SecurityTests                         # one test class
./mvnw test -Dtest='SecurityTests#protectedEndpointRejectsMissingToken'   # one test method (quote it in zsh)
./mvnw clean test                                        # use after renaming/moving classes; stale classes in target/ still run otherwise
./mvnw package                                           # build jar into target/
```

Frontend (`frontend/`):

```sh
npm run dev       # http://localhost:5173
npm run build     # type-check (tsc -b) + production build into dist/
npm run lint      # oxlint (not ESLint)
npm test          # Vitest
```

`npm test` runs Vitest (pure helpers only; there are no component or E2E tests).

## How the pieces connect

- The frontend calls the backend with relative `/api/...` URLs. In dev, the Vite proxy in `frontend/vite.config.ts` forwards `/api` to `localhost:8080`, so no CORS configuration exists in the backend. Keep backend REST endpoints under `/api` so the proxy covers them; adding CORS or absolute URLs is only needed if the apps are served from different origins in production.
- **Configuration** comes from the repo-root `.env` (git-ignored; template and docs in `.env.example`). Docker Compose reads it automatically; the backend imports it via `spring.config.import=optional:file:../.env[.properties]`, so `./mvnw` must run from `backend/`. Properties reference the variables as `${VAR:default}`. A variable present but empty overrides the default, so leave unused ones commented out. When adding a new variable, add it to `.env.example` too, and tell the user which value they need to fill in.
- Database selection is profile-driven:
  - Default profile (`application.properties`): in-memory H2 in PostgreSQL mode, H2 console at `/h2-console`, data lost on restart. Tests run on this profile, so they need no Docker.
  - `postgres` profile (`application-postgres.properties`): reads `DB_URL`, `DB_USERNAME`, `DB_PASSWORD`, defaulting to the `docker-compose.yml` database.
- **Schema is owned by Flyway.** Every schema change is a new file `backend/src/main/resources/db/migration/V<n>__<description>.sql`; never edit a migration that has been committed. Hibernate runs with `ddl-auto=validate`, so the app fails to start if entities and tables disagree. Migrations run on both H2 and PostgreSQL, so write portable SQL; generate UUID ids in the application (`GenerationType.UUID`), not with database functions.
- **Authentication is stateless JWT** (`security/`). `JwtService` issues HS256 access tokens (subject = user id, `email` claim, 15 min TTL); Spring Security's OAuth2 resource server validates the `Authorization: Bearer` header. Everything is authenticated except `PUBLIC_PATHS` in `SecurityConfig` (`/api/auth/**`, health, H2 console). In controllers take `@AuthenticationPrincipal Jwt jwt` and pass `CurrentUser.id(jwt)` to the service. Config: `workhub.jwt.*` and `workhub.auth.*`; set `JWT_SECRET` (≥ 32 bytes), `REFRESH_COOKIE_SECURE=true` and `FRONTEND_BASE_URL` outside local development.
- **Refresh and one-time tokens** (`auth/UserTokenService`, table `user_tokens`, only SHA-256 hashes stored). The refresh token is an HttpOnly, SameSite=Strict cookie `workhub_refresh` with path `/api/auth` (`RefreshCookies`) and rotates on every `/api/auth/refresh`. Two distinct states: `consumed_at` = redeemed (rotated); `revoked_at` = invalidated (logout, password change/reset, superseded link). Presenting a *consumed* refresh token is treated as theft and revokes all of that user's refresh tokens; a *revoked* one is just rejected (another device may still hold it). `AuthService.refresh` uses `noRollbackFor = ApiException.class` so that revocation commits while the request still fails, which is also why `UserTokenService` is deliberately not `@Transactional`. `UserTokenRepository.revokeAll` clears the persistence context, so modify entities before calling it.
- **Email** goes through the `EmailSender` interface. The only implementation, `LoggingEmailSender`, writes the message to the backend log, so in dev the verification/reset links are found in the backend console. Links point at `FRONTEND_BASE_URL` routes `/verify-email?token=` and `/reset-password?token=`.
- **Errors** are `ApiException(status, code, message)`, rendered by `GlobalExceptionHandler` as RFC 9457 problem details with a stable `code` (plus `errors` field map for validation). The frontend maps `code` to Vietnamese text in `frontend/src/api/errors.ts`; add new codes there.
- **Authorization (RBAC) goes through `access/AccessService`.** A service method takes the caller's id, calls `access.workspace(userId, wsId)` or `access.team(userId, teamId)`, then `.require(Permission)` (403 `FORBIDDEN`) and, for team writes, `.requireActive()` (409 `TEAM_ARCHIVED`). Outside the caller's workspaces everything is 404 (`WORKSPACE_NOT_FOUND` / `TEAM_NOT_FOUND`) so ids cannot be probed. Roles map to permission sets in the role enums: `WorkspaceRole` (OWNER = all, ADMIN, MEMBER = VIEW) → `WorkspacePermission`; `TeamRole` (LEAD, MEMBER) → `TeamPermission`. Workspace roles with `MANAGE_TEAMS` act as lead of every team (`TeamAccess.permissionsFor`); **a plain workspace member sees only the teams they belong to** (empty permission set = 404 `TEAM_NOT_FOUND`), so someone invited to one team or one project works only there. `GET /api/me/teams` and `/api/me/projects` list everything the caller can reach across workspaces (top-bar pages Team and Dự án), each with `mine` (the caller created it) so the pages split "của bạn" from "được mời"; the Workspaces page splits on `myRole === 'OWNER'`. **Guests**: accepting a team or project invitation adds the person to the workspace as a *guest* (`workspace_members.guest`, V21): the workspace is not listed for them and `GET /api/workspaces/{id}` and its member list answer 404; a workspace invitation (or being added) turns a guest into a full member with the invited role. Responses include the caller's `permissions` so the UI can hide actions; never rely on that for security. Projects follow the same pattern: `ProjectRole` → `ProjectPermission`, resolved by `access.project(userId, projectId)` into a `ProjectAccess`.
- **Project access** (`ProjectAccess.permissionsFor`): whoever has team `MANAGE_PROJECTS` (team LEAD, workspace OWNER/ADMIN) gets every project permission on that team's projects, without being a member; otherwise the member's `ProjectRole` decides; other members of the owning team get VIEW only; anyone else gets 404 `PROJECT_NOT_FOUND` (an empty permission set means no access, and list endpoints filter on it). Roles: PROJECT_MANAGER (all), PRODUCT_OWNER, SCRUM_MASTER, DEVELOPER, QA_ENGINEER, STAKEHOLDER. M3 enforces only VIEW / UPDATE_PROJECT / MANAGE_MEMBERS; MANAGE_BACKLOG, MANAGE_SPRINTS, EDIT_ISSUES and COMMENT are defined for M4+ and should be checked with `.require(...)` there.
- Project rules: `key` (2–10 chars, stored upper-case, unique per workspace) is immutable because issue keys (`ECOM-12`) will be built from it. **A member can hold several project roles** (`project_members` has one row per (project, user, role), V19; permissions are the union, `ProjectAccess.projectRoles`; responses carry `role` = the most powerful and `roles`/`myRoles` = all; `PUT /members/{userId}` takes `{roles: [...]}` and replaces the set). PROJECT_MANAGER and SCRUM_MASTER have exactly one holder (`ProjectRole.isSingleHolder`): giving one to someone else **moves it** (the previous holder keeps other roles or becomes DEVELOPER) and the manager cannot drop the role or leave without handing it over (409 `LAST_PROJECT_MANAGER`); invitations never take a held single-holder role (409 `ROLE_TAKEN`, or DEVELOPER if it was taken before they accepted). PRODUCT_OWNER can be held by several people. Status can move freely between PLANNING / ACTIVE / ON_HOLD / COMPLETED / ARCHIVED; ARCHIVED is read-only (`requireActive()`, 409 `PROJECT_ARCHIVED`) and only `changeStatus` is still allowed. The column is `project_key` because `key` is a JPQL function name. List queries (`ProjectRepository.ROWS`) compute member count with a scalar subquery; the caller's roles are loaded by one extra query (`findRolesOfUser`). **Project picture**: `PUT/DELETE /api/projects/{id}/avatar` (multipart `file`, JPEG/PNG/WebP ≤ 512 KB, needs UPDATE_PROJECT, table `project_avatars`, served publicly at `/api/public/projects/{id}/avatar?v=`); `PUT /api/projects/{id}` no longer takes `avatarUrl` and leaves the picture alone. UI: `ProjectPicture` in the project settings.
- **Issues** (`issue/`): `IssueService` (CRUD, status, assign, backlog order, stats, history), `IssueCollaborationService` (comments, checklist), `IssueFilter` (JPA `Specification` for backlog filters), `IssueMapper` (entities → responses with a fixed number of queries), `IssueLoader` (issue + the caller's `ProjectAccess`; unseen issues answer 404 `ISSUE_NOT_FOUND`). Permissions: EDIT_ISSUES creates/edits/assigns/changes status, MANAGE_BACKLOG reorders and deletes, COMMENT comments, all writes need an active (non-archived) project.
  - **Keys**: `projects.issue_counter` is bumped by one atomic `UPDATE` (`ProjectRepository.incrementIssueCounter`, which clears the persistence context) and read back; the row lock serializes concurrent creates, which also makes the rank calculation for new issues safe. The key is `<project key>-<number>`, built in `IssueMapper`; numbers are never reused.
  - **Hierarchy** (`IssueType.allowedParents`): Epic (top) > Feature > Story/Task/Bug/Spike > Sub-task (parent required). Parent must be in the same project; changing type is refused if existing children would become invalid. The nearest epic ancestor is resolved up to 3 levels (`IssueMapper`).
  - **Backlog order** is `backlog_rank` (gap 1024): `PUT /issues/{id}/rank {afterIssueId}` places the issue after another (null = top) by taking the midpoint, and rebalances the whole project when the gap is gone. There is no locking on moves; ties break by id.
  - **History is data**: every change is an `issue_activity` row (field, old, new; long text fields record only that they changed). Status changes also maintain `started_at` / `done_at`. Only `DONE` counts as done. Issues are soft-deleted (`@SQLRestriction("deleted_at is null")` on `Issue`, so every query and bulk update ignores them); deleting needs no live children. Sprint scope tracking (M5) and burndown (M6) must build on this history rather than on current state.
  - Statuses are the fixed `IssueStatus` enum for now (configurable per-project workflow is planned with the board). Not built yet: attachments, work log, issue links, watchers.
  - Leaving a project or workspace unassigns the user's issues (`IssueRepository.unassign*`). Assignees must be project members.
- **Sprints** (`sprint/`, Scrum projects only; MANAGE_SPRINTS = PO, SM, PM; everything needs an active project): lifecycle FUTURE → ACTIVE → COMPLETED, or CANCELLED. One ACTIVE sprint per project (starting takes `SprintRepository.lockProject`, a `SELECT … FOR UPDATE`, so two starts cannot both pass). A sprint lasts at most one month, needs ≥ 1 issue to start, and freezes `committed_points/issues` at start. EPICs and DONE issues cannot be planned; adding an issue that sits in another open sprint moves it.
  - **Membership history**: `issues.sprint_id` is the current pointer, `sprint_issues` is the append-only history (added_at/by/points, `added_after_start` = scope creep, removed_at/reason/points, final status/points at completion). Rows are closed, never deleted. Completing a sprint records each issue's final status, counts only `DONE` as done, and sends the rest to the backlog or a chosen FUTURE sprint (reason `CARRIED_OVER`; the carry-over is not scope creep). Done issues keep pointing at the completed sprint.
  - **Snapshots** (`sprint_snapshots`, one row per active sprint and day, last write of the day wins) are the input of the burndown/burnup/CFD charts (M6). `SprintSnapshotService.capture` runs on start, scope changes and complete; `IssueService` publishes `IssueChangedEvent` when a sprint issue's status or story points change and `SprintSnapshotService` listens (synchronously, same transaction). `capture` first locks the sprint row (`lockSprint`) so concurrent writers serialize and the day's row is never lost or duplicated. "Day" is computed in `workhub.time-zone` (default `Asia/Ho_Chi_Minh`, `TIME_ZONE` env var); timestamps stay UTC.
  - `SprintStats` computes live counts for open sprints and counts from the recorded outcome for closed ones. Issues in an open sprint cannot be deleted (409 `IN_SPRINT`); a project cannot switch to Kanban while it has open sprints.
- **Board & workflow** (`board/`): the board for Scrum is the active sprint's issues, for Kanban the project's non-epic issues (finished ones drop off after 14 days). Moving a card is the ordinary `PUT /issues/{id}/status`. `blocked`/`blocked_reason` live on the issue (`PUT /issues/{id}/blocked`). The workflow is still the five fixed `IssueStatus` values; a project can only rename them and hide CODE_REVIEW / TESTING (`workflow_statuses`, rows appear once customised; `WorkflowService` supplies the Vietnamese default names and rejects hiding a status that still has issues, and `IssueService.changeStatus` rejects hidden ones). Fully custom statuses are not supported.
- **Reports** (`report/`, any caller who can see the project; outsiders get 404): `GET /api/sprints/{id}/charts` (one row per calendar day from `sprint_snapshots`, built by `SprintChartBuilder`), `/api/projects/{id}/reports/velocity | lead-time?days= | workload | bug-trend?weeks=`. Charts come from recorded history, not current state: days without a snapshot carry the last state forward, days after today (or after completion) have `actual=false` and null numbers so the line stops instead of dropping to zero. The ideal line runs from the scope committed at start to 0 over working days (Mon-Fri) and is derived, not stored. Velocity is the last 10 COMPLETED sprints (committed vs completed points) and the mean of the last 3. Lead time = created→done, cycle time = started→done (issues never started have no cycle time); percentiles are nearest-rank. Workload is a live view of open non-epic issues per assignee. `ReportRepository` returns projections (`ReportRows`), never entities. Not built: Epic burndown and Release burndown (no release model yet).
- **Documents** (`document/`): per-project Markdown documents, folders, version history, file attachments and links to issues/sprints. Permission `EDIT_DOCUMENTS` (every project role except STAKEHOLDER; the manager has all) creates/edits/archives/links/uploads; reading needs only project VIEW; deleting needs to be the author or `UPDATE_PROJECT`; every write needs an active project. Outsiders get 404 (`DOCUMENT_NOT_FOUND`/`FOLDER_NOT_FOUND`).
  - **Versions are history**: `document_versions` is append-only and stores the full title+text. Creating makes v1; every change to title or text makes the next number (type/folder-only changes make none); restoring an old version adds a *new* version with its text (note "Khôi phục từ phiên bản n"), never rewrites. `documents.version_number` points at the newest.
  - **No silent overwrite**: `PUT /api/documents/{id}` carries `baseVersion`; a stale one is refused with 409 `DOCUMENT_CONFLICT`, and `@Version` (`lock_version`) catches two saves racing on the same base (exactly one wins). The UI then offers "take latest" or "keep mine and save over". This is a stop-gap until collaborative editing (M10, Yjs/CRDT) replaces whole-text saves.
  - Content is plain text/Markdown up to 100,000 chars (`TEXT` column). Soft delete (`@SQLRestriction`, like issues); ARCHIVED is read-only until unarchived and hidden from the default list (`status=` filter). Search `q` matches title or text, case-insensitive, `%`/`_` escaped. Folders: at most 4 levels, unique name per parent, deleted only when empty (409 `FOLDER_NOT_EMPTY`).
  - **Attachments** live in `document_attachments` (bytea, ≤ 10 MB each, ≤ 20 per document; `spring.servlet.multipart.*` limits, `FILE_TOO_LARGE` 413 comes from `GlobalExceptionHandler.handleMaxUploadSizeExceededException`; Tomcat may instead drop the connection for files far above the limit, so the UI checks the size first). Downloads need the bearer token and are always sent as `application/octet-stream` + `Content-Disposition: attachment`, whatever type was uploaded; lists use the `AttachmentRow` projection so bytes are never loaded. Links point at ISSUE/SPRINT of the same project (`target_id` is not a foreign key; deleted targets are simply not shown); MEETING joins with M8.
- **Meetings & calendar** (`meeting/`): permission `MANAGE_MEETINGS` (every role except STAKEHOLDER) schedules meetings, writes minutes and manages action items; changing a meeting's details, cancelling or deleting needs the organizer or `UPDATE_PROJECT`; reading needs project VIEW; writes need an active project; outsiders get 404 `MEETING_NOT_FOUND`. Stakeholders can be invited and reply (`PUT /meetings/{id}/response`, only for people on the list, else 403 `NOT_AN_ATTENDEE`).
  - Times are `Instant`s (UTC); the browser converts to and from local time. A past meeting is just SCHEDULED with a start in the past; only CANCELLED is stored. Organizer and attendees must be project members (the caller may organize without being one); at most 24 h; online link must be http(s). Saving the attendee list replaces it but keeps the replies of people who stay; the organizer is never listed as an attendee.
  - **Templates** (`MeetingTemplates`, `GET /api/meeting-templates`): one per `MeetingType` with default length, agenda and a minutes outline, all suggestions the organizer edits. The form prefills agenda and length from the chosen template; the minutes editor can insert its outline.
  - **Minutes** (`meetings.minutes`, Markdown): `PUT /minutes` carries `baseRevision`; the write is a single conditional `UPDATE … WHERE minutes_revision = :base` (`MeetingRepository.updateMinutes`), so two note-takers cannot both win (409 `MINUTES_CONFLICT`). There is no version history for minutes.
  - **Action items** (owner, deadline, OPEN/DONE) can be turned into a TASK with `POST /meeting-action-items/{id}/create-task` (carries owner and deadline, needs `EDIT_ISSUES` through `IssueService.create`; 409 `ALREADY_CONVERTED` the second time). `IssueService.create` clears the persistence context (the issue-counter bulk update), so re-load the item before setting `issue_id` (see `MeetingService.createTask`).
  - **Calendar** (`GET /api/projects/{id}/calendar?from&to&personId`, window ≤ 100 days): meetings, sprints (date ranges, cancelled ones skipped) and issue due dates in one list; `personId` keeps that person's meetings (organizer or attendee) and assigned issues. Days are cut in `workhub.time-zone`, so the browser asks for a window one day wider than it shows. Not built: Team calendar (across a team's projects), milestones/release dates, external calendar sync, PDF export of minutes (planned with export in M10).
  - Documents can be attached to meetings (`LinkTargetType.MEETING`); the meeting page lists them through `RelatedDocuments`.
- **Notifications** (`notification/`): `NotificationService.notify(recipient, type, title, body, link, projectId, actorId, dedupeKey)` is what other modules call. It runs inside the caller's transaction (a rolled-back change leaves no notification); the WebSocket push and the email happen after commit (`NotificationDelivery`, `@TransactionalEventListener(AFTER_COMMIT, fallbackExecution = true)`) and never fail the caller. Rules built in: nobody is notified about their own action (`recipient == actor` is skipped), a `(user, dedupeKey)` pair is delivered at most once (unique index), and per-user preferences (`notification_preferences`, overrides only; defaults per type in `NotificationType`, email defaults on for the important ones) decide in-app/email; both off = nothing. Emails go through `EmailSender` (still `LoggingEmailSender`, i.e. only the backend log, until SMTP is added). Triggers live where the change happens: `IssueService` (assigned, status changed, blocked), `IssueCollaborationService` (comment, `mentions` on `CommentBody`, must be project members), `ProjectService`/`TeamService.addMember`, `SprintService.start/complete`, `MeetingService` (invited, cancelled), chat mentions, and the jobs below. Endpoints: `/api/notifications` (+`unread-count`, `{id}/read`, `read-all`) and `/api/notification-preferences`. Messages are written in Vietnamese in the backend.
- **Progress alerts** (`alert/`): `AlertEvaluator` is pure reading (never notifies) and applies the project's thresholds (`project_alert_settings`, defaults in `AlertSettings.Values.defaults()`, 0 = rule off, edited with `PUT /alert-settings` by `UPDATE_PROJECT`): overdue, due soon (N days), no progress (in-progress issues untouched N days), blocked, overload (> N open issues per person), sprint at risk (≤ N days left and ≥ X% of points not done), scope change (points added after start ≥ X% of the commitment). `GET /api/projects/{id}/alerts` shows them live to any project member (the "Cảnh báo tiến độ" card); `AlertService.run()` turns them into notifications once per (person, finding[, day]) via dedupe keys (e.g. `OVERDUE:{issue}:{dueDate}`, `SPRINTRISK:{sprint}:{date}`, scope change once per 10% step). Recipients: the assignee, or the leaders (PM/SM/PO) for unassigned work, sprint rules and overload. These are risk signals, not verdicts.
- **Background jobs** (`alert/Schedulers`): alerts hourly (`workhub.alerts.cron`), meeting reminders every minute (`workhub.reminders.interval`, `MeetingReminderService`: organizer and non-declined attendees, once per meeting+start time). `workhub.scheduling.enabled=false` switches them off; surefire sets it so tests call the services directly.
- **Structure is live**: `StructureChangeInterceptor` (realtime/) sends `structure.changed {workspaceId, actorId}` (no data) to everyone with a membership row in the workspace (guests included) after any successful write under `/api/workspaces/**`, `/api/teams/**` and a project's own record/status/avatar/members/invitations (not its issues etc.); the audience is read *before* the handler so a deletion or a removed member is still told. `useInvitationsLive` listens to this event too, so the workspace/team/project lists and detail pages reload by themselves; a page whose record was deleted shows the not-found message with a link back.
- **Invitations are live**: `InvitationService` publishes `InvitationRealtime.Changed` (after commit → WebSocket `invitations.changed {workspaceId, teamId, projectId}`, no data) to the invitee (by email), the workspace members and the actor; `useInvitationsLive(reload)` reloads the invitation inbox, pending lists and member lists.
- **Realtime** (`realtime/`): one WebSocket endpoint `/ws` (`RealtimeSocketHandler`, public in `SecurityConfig` because the handshake cannot carry the bearer token). The first frame must be `{"type":"auth","token":"<access token>"}` (10 s timeout, never put the token in the URL); then `subscribe`/`unsubscribe {projectId}` (checked with `AccessService`; refused with an `error` frame) and `ping`. Only the app's own origin (`workhub.auth.frontend-base-url`) may connect. `RealtimeHub` holds sessions per user (multi-tab), wraps each in `ConcurrentWebSocketSessionDecorator`, delivers `sendToUser/sendToUsers/sendToProject` best-effort (slow sessions are dropped; clients reconnect and reload). Events: `notification`, `chat.message|message.updated|message.deleted|read`, and `project.changed {projectId, area, actorId}` which carries no data (clients reload what they show) and is published by `ProjectChangeInterceptor` after any successful write under `/api/projects/{id}/…` or `/api/{issues|sprints|documents|document-folders|meetings|meeting-action-items}/{id}…`; `ProjectLookup` finds the project with native SQL so soft-deleted records still resolve (H2 returns UUIDs as bytes, hence `toUuid`). `GET /api/presence?userIds=` says who has an open socket.
- **Chat** (`chat/`): conversation kinds PROJECT and TEAM (one per project/team, created on first listing; PROJECT readable by anyone who can see the project, TEAM by team members), DIRECT (one per pair, unique `direct_key`, no workspace: `conversations.workspace_id` is null since V20; people are found by exact email with `GET /api/chat/find-person?email=` and opened with `POST /api/chat/direct {userId | email}`) and GROUP (own member list, workspace members only, ≤ 50). Everything else is 404 `CONVERSATION_NOT_FOUND`. Messages: ≤ 4000 chars, reply-to (same conversation), `mentionIds` (must be in the conversation; they get a MENTIONED notification), edit/delete only by the sender (delete is soft, the text is hidden), reactions toggle per (message, user, emoji), history paged backwards with `before`. **Unread**: `conversation_reads.last_read_at` per user; a user without a row has nothing unread (project/team channel rows are created the first time the user lists them, DIRECT/GROUP rows when they join); sending a message marks the conversation read for the sender; own and deleted messages never count. Search (`/api/chat/search?q=`) covers only conversations the user can access, `%`/`_` escaped. **Attachments**: `POST /api/chat/conversations/{id}/attachments` (multipart `files`, up to 10, ≤ 10 MB each and ≤ 30 MB in total, optional `body` caption and `replyToId`; table `chat_attachments` with `position`; `spring.servlet.multipart.max-request-size` is 31 MB for this) makes a normal message whose `attachments` list keeps the upload order; without a caption the body is `📎 <file name>` (one file) or `📎 N tệp`, so previews, search and notifications need no special case, and the UI hides exactly that text under the files. `GET /api/chat/attachments/{id}` needs the bearer token and access to the conversation, is always `application/octet-stream` + `attachment`, and 404s once the message is deleted. An image type is only kept (`image: true`) when the magic bytes match PNG/JPEG/WebP/GIF, otherwise it is stored as an opaque download; the UI (`MessageAttachment`) fetches images as blobs. **Typing**: the client sends the WebSocket frame `chat.typing {conversationId}` (at most every 2.5 s while the draft is non-empty); `ChatService.typing` (deliberately `NOT_SUPPORTED`, so a refused access check cannot poison a transaction) checks access, throttles to one relay per 1.5 s per person and conversation and sends `chat.typing {conversationId, userId, name}` to the other members; nothing is stored, the UI shows waving dots for 4 s and drops them when that person's message arrives. **Seen**: `GET /api/chat/conversations/{id}/receipts` returns each other member's `lastReadAt` (from `conversation_reads`), and `markRead` broadcasts `chat.seen {conversationId, userId, at}` to the others; the UI shows "Đã xem" (avatars in groups) under the last of the caller's messages each reader has reached. The conversation list (`ChatPage`) listens to `chat.typing` for every conversation and shows the waving dots with "X đang nhập…" in place of the last-message preview (`pages/chat/typing.ts` builds the label). Not built: per-message (rather than per-conversation) read state.
- **Audit log** (`audit/`): append-only `audit_log` (nothing in the app updates or deletes a row), with actor and target names copied in so it stays readable after renames/deletes. What is recorded is decided by the whitelist in `AuditCatalogue` (method + path template → action code; only administrative and security-relevant routes: roles and membership, structure of workspaces/teams/projects, sprint lifecycle and scope changes, deletions, restores, **data exports**, sign-up/sign-in/password change). Everyday work (comments, chat, status moves, ranking) is deliberately not there; add a rule to audit another endpoint. It is written by `AuditFilter` (only wraps matched requests, runs after Spring Security so the token is known) via `AuditRecorder` after the controller answered: successful requests only, except rules with `failures(...)` (a failed sign-in becomes `auth.login_failed`, and only for emails that belong to an account, so nobody can flood the table). Creations take the new id and workspace from the response body; deletions still resolve names through native SQL (`AuditLookup`, soft-deleted rows included). Details are limited to a few whitelisted request keys (role, status, kind, email…); passwords and tokens never reach it, and a failure in the recorder is logged, never thrown into the request. Reading: `GET /api/workspaces/{id}/audit-log` (+`/export`) needs the new workspace permission `VIEW_AUDIT` (OWNER, ADMIN), `GET /api/projects/{id}/audit-log` needs `UPDATE_PROJECT`, `GET /api/me/audit-log` is everyone's own trail. Filters: actor, action (exact or a family ending in a dot such as `project.`), project, text, dates, outcome. Retention: `AuditRetentionService.purge()` (daily 03:15, `workhub.audit.purge-cron`) deletes entries older than `workhub.audit.retention-days` (`AUDIT_RETENTION_DAYS`, default 730, 0 = keep all); it is the only code that deletes audit rows.
- **Export** (`export/`): `Table` → CSV (UTF-8 with BOM so Excel reads Vietnamese, CRLF, quoting) or XLSX (`XlsxWriter`, ~150 lines, no library: one sheet, bold frozen header, typed cells, inline strings; verified by opening it with openpyxl). Both defuse spreadsheet formulas (text starting `= + - @` gets a leading `'`, numbers are untouched). `ExportService` builds every table through the service that already guards the data (`IssueService.list`, `SprintService.report`, `ReportService`, `ProjectService`), so who may export is exactly who may read; endpoints under `/api/projects/{id}/export/{issues|members|velocity|lead-time|workload|bug-trend}`, `/api/sprints/{id}/export[/daily]`, `/api/workspaces/{id}/export/{projects|members}`, `/api/teams/{id}/export/projects`, all `?format=csv|xlsx` (400 `INVALID_FORMAT` otherwise); issues take the backlog filters plus `createdFrom/To`. Exports are themselves audited. Charts leave as SVG/PNG from the browser (`components/charts/exportChart.ts` inlines computed styles, drops `var()` attributes, PNG at 2x) and PDF is the browser's print dialog with a print stylesheet that hides the app chrome (`PrintButton`, `@media print` in `index.css`); no server-side PDF library or font is bundled.
- **Collaborative editing** (`document/Collab*`, frontend `pages/documents/collab/`): Yjs/CRDT, as the spec requires. The server never interprets Yjs data: `document_updates` is an ordered log of binary updates and `document_collab` holds the latest full-state snapshot uploaded by a client plus its `snapshot_seq`; `documents.content` stays the plain-text working copy (search, lists, export, versions). Live traffic uses the existing WebSocket: `doc.join` (access checked; the reply says `canEdit` and `init`), `doc.update` (stored, numbered, relayed to the others, `doc.ack` to the sender), `doc.awareness` (cursors/names, relayed and remembered for late joiners, `doc.peer_left` removes them), `doc.reset`, `doc.init`, `doc.error`. Rooms and the init lease live in memory in `CollabSessions` (one server instance). **Seeding**: an empty CRDT whose document already has text must be filled exactly once, so the server hands that job (`init`) to the first editor and moves it if they leave first. **Snapshots** (`POST /collab/snapshot`, debounced ~6 s after changes) are accepted only if they cover at least as many updates as the stored one (a client that is behind cannot move the text backwards), then the updates they contain are deleted; they refresh `content` and add a version only when asked (`createVersion`) or when the text changed and the last version is ≥ 10 min old. **Epoch**: restoring a version or saving plain text through `PUT /documents/{id}` bumps it (`CollabService.reset`, event after commit → `doc.reset` to every open editor, which reload); updates/snapshots naming an old epoch are refused (`STALE_EPOCH`). `GET /collab` returns the state under a shared row lock so a snapshot cannot interleave; viewers (no `EDIT_DOCUMENTS`, archived document or project) join read-only. Title/type/folder use `PUT /collab/meta`. Frontend: `CollabSession` (Yjs doc + awareness + sync/reconnect logic; attaches its update listener *before* the first sync or the seeding update is never sent; a replaced session must not send `doc.leave` after the new one joined, see `active`), `CollabEditor` (CodeMirror 6 + `y-codemirror.next`, lazy-loaded chunk ~600 kB, presence chips, "Lưu vào lịch sử", "Xong" flushes). The old draft editor with `baseVersion` conflict handling is gone from the UI (the REST `PUT` with `baseVersion` still exists for API use). Not built: comments/@mentions inside documents, rich-text editing (it is Markdown source), tests for editing while offline.
- **Hardening & deployment (M11)**: `security/RateLimitFilter` limits `POST /api/auth/{login,register,forgot-password,reset-password,verify-email}` per client address (`workhub.rate-limit.*`, default 20/min, in memory, 429 `RATE_LIMITED` + `Retry-After`; `/refresh` is exempt; surefire raises the limit, `RateLimitTests` sets its own). `SPRING_PROFILES_ACTIVE=prod` (a profile group: `postgres` + `prod`) trusts `X-Forwarded-*`, exposes only `/actuator/health` without details, hides error messages, and `ProductionGuard` refuses to start with the dev JWT secret, a non-Secure refresh cookie or a non-https `FRONTEND_BASE_URL`. `backend/Dockerfile`, `frontend/Dockerfile` (nginx: SPA fallback, `/api` and `/ws` proxy, CSP and security headers in `frontend/deploy/nginx.conf`) and `docker-compose.prod.yml` (postgres + backend + web; TLS must be terminated in front of `web`; verified by building and running it) deploy the app; `.github/workflows/ci.yml` runs backend tests, frontend lint/test/build and both image builds. Frontend tests use Vitest (`npm test`, `*.test.ts` next to the code). V16 adds indexes for foreign keys that queries filter on. The nginx limit/`client_max_body_size` should match the backend's 10 MB attachment limit.
- **Email** is `SmtpEmailSender` (Spring Mail, plain text UTF-8, sent on its own thread, a failure is only logged) when `MAIL_ENABLED=true` (+ `MAIL_FROM`, `SMTP_HOST/PORT/USERNAME/PASSWORD`, STARTTLS), otherwise `LoggingEmailSender` (the two are chosen by `@ConditionalOnProperty workhub.mail.enabled`). The mail health indicator is off so an SMTP outage never turns `/actuator/health` red.
- **Deleting** (`CascadeCleaner` first cuts the foreign keys without cascade between rows deleted together (`sprint_issues.issue_id`, `issues.sprint_id/parent_id`); PostgreSQL refuses otherwise: `DELETE /api/workspaces/{id}` needs `DELETE_WORKSPACE` = OWNER; `DELETE /api/teams/{id}` needs `DELETE_TEAM` = team LEAD and workspace OWNER/ADMIN): the body `{name}` must equal the current name (`DeleteConfirmation`, 400 `NAME_MISMATCH`). Everything below goes through the schema's `ON DELETE CASCADE` (verified on H2 and PostgreSQL in `DeletionTests`); the workspace's audit rows cascade too, so `workspace.delete` is recorded without a workspace scope (it stays in the actor's `/api/me/audit-log`, name taken from the confirmation). UI: `components/DeleteZone` (type the name to enable the button). Rename/edit already existed (`PUT`) and archive is the soft alternative for teams.
- **Account deletion** (`DELETE /api/me {password}`, `user/AccountDeletionService`): anonymises instead of deleting the row (documents, issues, messages and audit rows point at it): memberships, assignments, attendances, notifications, preferences, chat membership/reads/reactions, avatar and tokens are removed, pending invitations to the address are revoked, and the user becomes `deleted-<id>@deleted.invalid` / "Người dùng đã xóa" with an unusable password (the real address can register again). A workspace OWNER gets 409 `OWNS_WORKSPACES` until they transfer or delete the workspace. Access tokens already issued stay valid for their 15 minutes (but the person has no memberships left); refresh tokens are gone. UI: "Xóa tài khoản" in the account menu.
- **Backups**: `scripts/backup.sh` (pg_dump custom format, keeps the newest `BACKUP_KEEP`) and `scripts/restore.sh` (drops the `public` schema, then pg_restore; asks to type `restore`, `ASSUME_YES=1` skips) work on the compose file in `COMPOSE_FILE`; `docker-compose.prod.yml` also runs a `backup` service (daily, `BACKUP_KEEP_DAYS`, volume `backups`). Copy dumps off the host.
- **Load test**: `node loadtest/load.mjs --users 30 --seconds 30` (no dependencies; start the backend with `RATE_LIMIT_ENABLED=false`). Measured once on a laptop with PostgreSQL: 30 users, 463 req/s, 0 errors, worst p95 12 ms.
- **E2E tests** (`frontend/e2e/`, Playwright, `npm run e2e`): `playwright.config.ts` starts the backend (H2, throwaway JWT secret, rate limit off) and Vite itself and reuses ones already running; locally the installed Google Chrome is used, CI installs Chromium (`e2e` job). Setup goes through the API (`e2e/support.ts`), the checked behaviour through the UI.
- Workspace rules: exactly one OWNER, who cannot be removed, demoted or leave; only the OWNER (`MANAGE_ADMINS`) changes roles or invites/removes admins; ADMINs invite/remove members and manage teams. Removing someone from a workspace also removes them from all its teams. **Ownership transfer**: `POST /api/workspaces/{id}/transfer-ownership {userId, password}` (permission `TRANSFER_OWNERSHIP`, OWNER only; the target must be a member, the owner's password is re-checked; the old owner becomes ADMIN, so there is still exactly one OWNER). UI: `TransferOwnership` on the workspace page.
- **Invitations** (`invitation/`): into a workspace (`teamId` null, `role` is a workspace role) or a team (`role` is a team role; accepting also adds the user to the workspace as MEMBER) or a project (`project_id` set, `POST/GET /api/projects/{id}/invitations`, needs project `MANAGE_MEMBERS` and an active project; `role` is a project role; accepting adds the user to the workspace as MEMBER and to the project, not to its team; a PRODUCT_OWNER/SCRUM_MASTER invite falls back to DEVELOPER if the single seat was taken meanwhile). The project Members page has the invite card. `EMAIL` = single use, only the account with that email can accept/decline, re-inviting revokes the older one; `LINK` = reusable until expiry (`workhub.invitations.ttl`, 7 days) or revocation. Only the token hash is stored, so the link is returned once at creation (`inviteUrl`). `EXPIRED` is derived from `expires_at`, never stored. Accepting never changes an existing membership's role. Unauthenticated endpoints live under `/api/public/**` (e.g. the invitation preview).
- `@CreationTimestamp` is filled on INSERT (at flush). When a create endpoint returns the new entity, use `saveAndFlush`, otherwise `createdAt` is null in the response.
- **Profile pictures** (`user/`): `PUT /api/me/avatar` (multipart `file`, JPEG/PNG/WebP, ≤ 512 KB, magic bytes checked) stores the bytes in `user_avatars` and sets `users.avatar_url` to `/api/public/users/{id}/avatar?v=<millis>`; `DELETE /api/me/avatar` removes it. The image endpoint is public (an `<img>` cannot send the bearer token) and cached for 30 days, the `v` parameter busts the cache. `PUT /api/me` only changes the name. The browser center-crops and downsizes to 256px JPEG before uploading (`api/resizeImage.ts`). Image bytes never travel in lists; they only carry the URL.
- Passwords: `PasswordEncoder` bean (delegating, bcrypt), 8–72 characters and at most 72 UTF-8 bytes (bcrypt limit; checked in `AuthService`).
- User emails are stored lower-cased; use `User.normalizeEmail` before saving or querying.
- Actuator is enabled; `/actuator/health` is the public health check.
- **Integrations** (`integration/`, V22): `POST /api/integrations/connect {email,password,register?}` (public, rate-limited) đăng nhập/đăng ký rồi trả token tích hợp `whk_…` (chỉ lưu SHA-256 trong `integration_tokens`); `POST /api/integrations/token {token}` đổi lấy access token thường 15 phút (nên mọi controller giữ nguyên). `issues.external_ref` (ví dụ `smartspec:usecase/<project>/<lineage>`) được nhận ở `Create`, trả ở `IssueResponse.externalRef`. Mọi ghi thành công vào dự án có issue có `externalRef` → `IntegrationOutbox.projectChanged` (gọi từ `ProjectChangeInterceptor`, bảng `integration_outbox` V23, gộp một dòng chờ/dự án) → `IntegrationJobs` mỗi giây gửi webhook `project.changed {projectId}` ký HMAC tới `workhub.integration.webhook-url` (backoff tối đa 12 lần). Payload không mang dữ liệu: ForgeBridge đọc lại trạng thái thật qua REST. **Managed documents** (V24 `documents.external_ref`): a document whose `externalRef` starts with `smartspec:` is read-only for people (`DOCUMENT_MANAGED` 403 on update/archive/delete/collab, `canEdit`/`canDelete` false, `managed` true in responses; attachments and links stay allowed); only requests carrying `X-Integration-Key` equal to `workhub.integration.webhook-secret` (`IntegrationGate`) may create/tag/change them, and the lock is off when no secret is set. `POST /api/integrations/connect` also returns `tokenId` (revoke with `DELETE /api/integrations/tokens/{id}`). `IssuePage` hiển thị nguồn SmartSpec (`VITE_SMARTSPEC_URL`) cho issue có `externalRef`.

- **One account with SmartSpec** (`integration/IdentityPeer`, V25 `users.password_changed_at`): when `workhub.integration.identity-url` is set, `AuthService.login` asks SmartSpec (through ForgeBridge) if the e-mail/password is valid there and creates the account here (or adopts a password changed there **only if newer** than ours); `register` refuses an address that exists in SmartSpec with another password (409 `EMAIL_TAKEN`); reset/change password is pushed to SmartSpec (`peer.setPassword`). The other system calls `POST /api/integrations/identity/verify|set-password` with `X-Integration-Key`.

## Spring Boot 4 notes

This project is on Spring Boot 4, where starters are split per feature and packages moved. For example, `@WebMvcTest`/`@AutoConfigureMockMvc` live in `org.springframework.boot.webmvc.test.autoconfigure`, and the JWT starter is `spring-boot-starter-security-oauth2-resource-server`. Check imports and starter names against Boot 4 (e.g. via start.spring.io) when adapting older examples.

## Backend tests

Integration tests use `@SpringBootTest` + `@AutoConfigureMockMvc`, so the real security config and Flyway schema apply. Helpers in `src/test/java/com/workhub/support/`:
- Do not name a test helper `post`, `get`, `status`, … (it has happened twice; `act`, `postIssue`, `setStatus` are the names used): it shadows the static MockMvc imports and fails with confusing "cannot be applied" errors. MockMvc encodes the URL template itself, so pass `%` raw in query strings. `TestApi.register(mockMvc)` creates a user with a random email and returns a session (`bearer()`, `refreshCookie()`, `userId()`); `TestApi.json(k, v, ...)` builds request bodies. `createWorkspace`, `createTeam` and `joinWorkspace(mockMvc, inviter, wsId, role)` (register + link invitation + accept) set up multi-user scenarios. All test classes share one H2 database, so always use fresh random emails, never fixed ones.
- `RecordingEmailSender` (a `@Primary` test component) captures emails; `lastToken(email, "/verify-email")` extracts the token from the last matching link.

## Frontend structure

- `src/api/client.ts` — `api<T>(path, {method, body})` for every backend call. It keeps the access token in memory only, attaches it (except on `/api/auth/*`, which must not get a possibly expired token), and on a 401 refreshes once and retries. `refreshSession()` dedupes concurrent calls into one request: parallel refreshes would trip the backend's reuse detection and sign the user out (React StrictMode double-runs startup effects in dev).
- `src/auth/` — `AuthProvider` restores the session on load via the refresh cookie; `useAuth()` exposes `ready`, `user`, `login`, `register`, `logout`, `setUser`. The context and hook live in `AuthContext.ts`, the component in `AuthProvider.tsx` (oxlint's `only-export-components`).
- `src/api/useResource.ts` — `useResource<T>(path)` → `{data, error, reload}` for loading data in pages; prefer it over hand-written fetch effects.
- Project pages are nested routes under `ProjectLayout` (`/projects/:id`, `backlog`, `sprints`, `sprints/:sprintId`, `board`, `members`, `settings`); child pages read the project through `useProject()` (Outlet context). Backlog, Sprint and Board are live; Documents/Meetings/Calendar/Reports tabs are placeholders until their milestones. Issue pages live at `/issues/:id` (outside the project layout) and fetch the project themselves.
- **Realtime/notifications UI**: `realtime/RealtimeProvider` owns the single WebSocket (auth in the first frame, ping every 25 s, reconnect with growing delay after fetching a fresh token, re-subscribes, emits a synthetic `reconnected`). Pages never talk to it directly: `useLiveReload(projectId, areas, reload)` subscribes to the project (reference-counted) and calls `reload` debounced when one of `areas` changes (and after a reconnect); `ProjectLayout` subscribes once for all project pages. `useUnread` keeps the bell/chat badges. `Layout` shows `NotificationBell` (panel), a "Đang nối lại…" chip only after 3 s offline, and `Toasts`. `/notifications` lists them and edits the per-type channel preferences. Vite proxies `/ws` with `ws: true`.
- **Chat UI** (`pages/chat/`): `/chat` and `/chat/:conversationId`; the project tab "Trao đổi" (`ProjectChatRedirect`) opens the project channel. `MessagePane` loads the newest page, appends/updates live, marks read, keeps the scroll position when older messages are prepended; the composer sends on Enter, `@` opens member suggestions (`mentions.ts` derives the mention ids from the final text). Issue comments take mentions through a "Nhắc đến…" selector.
- **Meetings UI** (`pages/meetings/`): `MeetingsPage` (upcoming/past, grouped by day), `MeetingForm` (template cards pick type, length and agenda; reused for editing), `MeetingPage` (details, RSVP, minutes, action items, linked documents) and `CalendarPage` (month grid, Monday first, with layer and person filters plus an agenda for the selected day; on phones the day cells show dots only). Datetime inputs use the browser's local time and convert with `toLocalInput`/`fromLocalInput`.
- **Documents UI** (`pages/documents/`): `DocumentsPage` (folder sidebar + filters + list) and `DocumentPage` (read / edit / version view with line diff / attachments / links / history) are nested project routes `documents` and `documents/:documentId`. `components/Markdown.tsx` is a small renderer that builds React elements (never raw HTML), so document text cannot inject markup; keep it that way. The one exception is ```` ```mermaid ```` fences: `MermaidDiagram` lazy-loads mermaid (securityLevel `strict`, which sanitises its SVG) and falls back to showing the source; SmartSpec's diagrams arrive this way. Table cells may contain `\|`. Files are downloaded with `downloadFile()` (fetch with the token, then save the blob) because a plain link cannot send the bearer header. `RelatedDocuments` shows the documents linked to an issue.
- **Charts** (`components/charts/`, hand-written SVG, no chart library): `TimeSeriesChart` (lines + stacked areas, crosshair/tooltip, arrow-key navigation), `ColumnChart`, `ScatterChart`, wrapped in `ChartShell` (title, legend, table view toggle). Series use three neutral tones `--chart-ink/mid/soft` (validated as an ordinal ramp with the dataviz skill's `validate_palette.js --ordinal`), so identity never relies on colour alone: legend + dash style + table view. Charts measure their container with `ResizeObserver` and draw at pixel size. The reports page is `pages/project/ReportsPage.tsx` (route `reports`, sub-views via `?view=`; Scrum-only views are hidden for Kanban).
- There is no profile page: the avatar in the top bar opens `components/AccountMenu` (edit name, choose/remove photo, change password, sign out). `api()` sends a `FormData` body as multipart. `Avatar` renders the photo or the initial.
- `src/components/Guards.tsx` — `RequireAuth` / `RedirectIfAuthenticated` route wrappers; signed-in pages render inside `Layout`. Pages pass `state={{ from }}` to `/login` and `/register` to come back afterwards (used by `/invitations/:token`).
- Status names always come from `useWorkflow(projectId)` (names + enabled statuses), never from the static `STATUS_LABELS`, which is only the fallback. `BoardPage` moves cards optimistically and then reloads; the sprint planning screen (`SprintPage`) shows the sprint backlog beside the unplanned backlog picker.
- Backlog rows with children show a ▸ toggle; opening it loads `GET /api/issues/{id}` and lists the sub-tasks nested under the parent (reloaded on live changes). `BacklogPage` keeps its own list state (filters → query string, optimistic updates after inline status/assignee changes and drag-and-drop reorder). Drag-and-drop is only enabled on the unfiltered, ungrouped list, because a rank move is defined relative to the full backlog.
- **Design system** (`src/index.css`, one file): black-and-white with a single ink colour (`--ink`; `--accent*` are aliases of it, so never add a coloured accent), Newsreader (serif) for `h1`/brand and Be Vietnam Pro for text, loaded from Google Fonts in `index.html`. Content is full width (`.page` has no max-width; gutter is `--gutter`). Radius by role: `--radius-field` 12px for inputs, `--radius` 20px for surfaces, pill (999px) for buttons/tabs/badges. Semantic colours (danger/success/warning) only for meaning. Take colours from the CSS variables (they flip in dark mode), not hex values. New pages should reuse the existing classes (`card`, `badge`, `row`, `tabs`, …) instead of adding styles.
- UI visibility follows the `permissions` arrays returned by the backend (see `WorkspacePage`, `TeamPage`), not role names.
- Single-use links (verify email) must guard against StrictMode's double effect with a `useRef` flag (see `VerifyEmailPage`).

The machine's JDK is 23; the build targets Java 21 (`java.version` in `pom.xml`).
